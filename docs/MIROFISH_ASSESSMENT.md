# MiroFish assessment (Milestone 1)

Source inspected: `github.com/666ghj/MiroFish` (`main`), files read directly: `README.md`, `backend/requirements.txt`,
`backend/app/services/simulation_runner.py`, `backend/scripts/action_logger.py`, `backend/scripts/run_parallel_simulation.py`,
`backend/app/services/simulation_config_generator.py`, and the route tables of `api/{graph,simulation,report}.py`.

## What MiroFish is

A "swarm-intelligence prediction engine". Seed material → knowledge graph → generated agent personas → social-media
simulation (Twitter/Reddit style) → prediction report → chat with agents / the report agent.

## Architecture as it actually is

| Layer | Implementation |
|---|---|
| Frontend | Vue 3 + Vite, five "Step" components (graph build → env setup → simulation → report → interaction) |
| Backend | Flask + flask-cors, three blueprints: `graph` (ontology, build, project), `simulation` (entities, prepare, start/stop, run-status, actions, timeline, interview), `report` (generate, chat, tools) |
| Graph / memory | **Zep Cloud** (`zep-cloud==3.25.0`): ontology generated by an LLM, text chunks pushed to a Zep graph, entities read back (`zep_entity_reader.py`), and agent actions are written back as memory (`zep_graph_memory_updater.py`) |
| Personas | `oasis_profile_generator.py` builds one OASIS profile per graph entity using an LLM + Zep search |
| Simulation config | `simulation_config_generator.py`: LLM produces time config, per-agent `activity_level`, `posts_per_hour`, `response_delay_*`, `sentiment_bias`, `stance`, `influence_weight`, and initial posts / hot topics |
| Engine | **OASIS** (`camel-oasis==0.2.5`, `camel-ai==0.2.78`). Launched as a *subprocess* (`scripts/run_{twitter,reddit,parallel}_simulation.py`). Each active agent makes an LLM call per round and chooses an OASIS `ActionType` (CREATE_POST, LIKE_POST, REPOST, QUOTE_POST, FOLLOW, CREATE_COMMENT, DISLIKE_*, SEARCH_*, TREND, MUTE, DO_NOTHING) |
| Event recording | The subprocess appends JSON lines to `<sim>/<platform>/actions.jsonl` (`round`, `timestamp`, `agent_id`, `agent_name`, `action_type`, `action_args`, `result`, `success`, plus `round_start`/`round_end`/`simulation_start`/`simulation_end`). `SimulationRunner._monitor_simulation` tails those files and keeps `run_state.json` |
| IPC | `simulation_ipc.py`: file-based command channel used for interviews of live agents |
| Reporting | `report_agent.py` (~100 KB): a ReACT-style agent with tools (`zep_tools.py`: search, statistics, interview) writing a sectioned report |
| LLM | Any OpenAI-SDK-compatible endpoint via `LLM_API_KEY / LLM_BASE_URL / LLM_MODEL_NAME` |
| Packaging | Docker + docker-compose; ports 3000 / 5001 |

## Findings relevant to ANVAYA

**Worth reusing (as concepts, and as an integration target)**
- The action vocabulary and the `actions.jsonl` event contract: simple, append-only, replayable.
- The two-stage "prepare → run" split and the idea of per-agent behavioural parameters
  (activity, stance, sentiment bias, influence weight).
- Interview-an-agent and report-agent-with-tools patterns.

**Limitations that drive redesign**
1. **No spatial / relational events.** Most OASIS actions are *broadcast-style* (post, like a post found in a feed).
   An action has an `agent_id` but frequently no explicit target agent, so a "who talked to whom" animation cannot be
   derived from raw logs. ANVAYA's normalised event schema has explicit `source_agent` / `target_agent`.
2. **Cost scales with agents × rounds** (one LLM call per active agent per round). On a free-tier provider limited to
   60 requests/minute that is impractical for hundreds of agents.
3. **Hard dependency on Zep Cloud** (proprietary, key required) for graph and memory. ANVAYA keeps its own local graph store.
4. **Python 3.11–3.12 only**, heavy dependency stack (camel-ai), file-based IPC, in-process thread monitor.
5. **No real-time push transport**: the Vue app polls `run-status` / `actions`.
6. **No live visualisation of the agent society**: the graph panel shows the knowledge graph, not agents interacting.
7. **No analytics layer** (cascades, polarisation, communities) and no scenario comparison.

## Decision

ANVAYA ships its own modular engine and treats MiroFish/OASIS as a *pluggable engine* behind the same event schema:

```
        ┌────────────── SimulationEngine interface ──────────────┐
        │  start(config) → async stream[NormalisedEvent]         │
        └───────────────┬───────────────────────┬────────────────┘
          NativeEngine (default)          MiroFishEngine (adapter)
          opinion dynamics + batched      normalises OASIS actions.jsonl
          LLM verbalisation               into ANVAYA events
```

`backend/anvaya/engines/mirofish.py` converts MiroFish `actions.jsonl` into ANVAYA events and is covered by unit tests
against the log format above. **It has not been run against a live MiroFish install** (that needs Python 3.11/3.12, `camel-oasis`
and a Zep Cloud key which were not available); this is stated in the README and the UI.
